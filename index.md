## 4. Working Agreements

### Rules we agree to follow as a team

- We show up prepared and on time for every ceremony.
- We respect timeboxes. Daily stand-ups must stay under 15 minutes.
- We give constructive, specific feedback focused on the work, not the person.
- We raise blockers early and do not struggle silently for more than half a day.
- We commit to continuous improvement and act on at least one retrospective action item per sprint.
- We never push directly to `main`. All changes must go through a pull request with at least one reviewer.
- We keep the Kanban or sprint board up to date at the end of every working day.
- We ask for help before missing a deadline.

## 7. Definition of Done (DoD)

### When is work really done?

A task or feature is considered complete when:

-  The code is written, compiles and runs locally without errors.
-  The code has been peer-reviewed through a pull request and approved by at least one other developer.
-  The feature is covered by at least one automated or documented manual test.
-  All tests pass, and no existing tests are broken.
-  Role-based access (Student / Lecturer / Administrator) is respected for any new endpoint or screen.
-  Features handling student data comply with basic POPIA requirements: collect only what is needed, restrict access and log sensibly.
-  The README or user documentation has been updated where relevant.
-  The Product Owner has accepted the work against its acceptance criteria.
-  The code is merged into `main` and deployed to the agreed demo environment (Vercel / Railway).
