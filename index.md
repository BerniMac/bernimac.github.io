## 1. Team Purpose & Vision

### Why do we exist as a team?

- **Team mission:** Build the QR Code Attendance Management System (QAMS), a web-based application that replaces slow, paper-based attendance registers with fast, fraud-resistant digital check-in for students, lecturers and administrators at CPUT. The system will be delivered as our Project Presentation 3 submission.

- **Success definition:** A working, deployed QAMS prototype that demonstrates time-limited QR code generation, real-time attendance capture, late-arrival flagging and role-based dashboards. The lecturer must approve the project at the final review, and every team member must be able to present and defend their contribution.

- **Product / Service:** A full-stack web application using Vue.js and Bootstrap for the frontend, Spring Boot REST API for the backend, and a MySQL database. The system will be hosted on free-tier cloud services and support Student, Lecturer and Administrator roles. Source code will be stored on GitHub, with a demo video provided.

## 3. Ways of Working

### How we work together day to day

### 3.1 Agile Framework

-  **Scrum:** Recommended because it fits the semester timeline with fixed sprints.
-  Kanban: Continuous flow without fixed sprints.
-  Scrumban: A hybrid approach combining Scrum ceremonies with a Kanban board.

### 3.2 Ceremonies

| Ceremony | Frequency | Purpose |
|---|---|---|
| Daily Stand-up | Daily (15 minutes) | Each member shares what they did, what they will do and what is blocking them. |
| Sprint Planning | Every 2 weeks | Select stories from the backlog and commit to a realistic sprint goal. |
| Review / Demo | End of each sprint | Demonstrate working software to the Product Owner or lecturer and collect feedback. |
| Retrospective | End of each sprint | Review how the team worked, identify what went well, decide what to improve and agree on one action item. |

---

## 4. Working Agreements

### Rules we agree to follow as a team

- We show up prepared and on time for every ceremony.
- We respect timeboxes. Daily stand-ups must stay under 15 minutes.
- We give constructive, specific feedback focused on the work, not the person.
- We raise blockers early and do not struggle silently for more than half a day.
- We commit to continuous improvement and act on at least one retrospective action item per sprint.
- We never push directly to `main`. All changes must go through a pull request with at least one reviewer.
- We keep the Kanban or sprint board up to date at the end of every working day.
- We ask for help before missing a deadline.

## 6. Decision-Making

### How decisions are made

- **Consensus:** The default for technical and process decisions.
-  **Product Owner final decision:** Used for scope and priority disputes.
-  Team vote (majority): Used when consensus cannot be reached in 10 minutes.
-  Agile Lead decides after input: Used for process and tooling disputes.

**Escalation path if we are stuck:**

Discuss in the daily stand-up → Raise the issue in the retrospective → Agile Lead calls a short decision meeting → Consult the lecturer as a last resort.

## 7. Definition of Done (DoD)

### When is work really done?

A task or feature is considered complete when:

-  The code is written, compiles and runs locally without errors.
-  The code has been peer-reviewed through a pull request and approved by at least one other developer.
-  The feature is covered by at least one automated or documented manual test.
-  All tests pass, and no existing tests are broken.
-  Role-based access (Student / Lecturer / Administrator) is respected for any new endpoint or screen.
-  Features handling student data comply with basic POPIA requirements: collect only what is needed, restrict access and log sensibly.
-  The README or user documentation has been updated where relevant.
-  The Product Owner has accepted the work against its acceptance criteria.
-  The code is merged into `main` and deployed to the agreed demo environment (Vercel / Railway).

- **Available development time:** Approximately 120–160 developer hours distributed across six team members working part-time.
